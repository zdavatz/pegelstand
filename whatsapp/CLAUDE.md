# WhatsApp integration & Pump Tsüri Welcome

Guidance for the `whatsapp/` scripts and the `sync-contacts` / `welcome` flow. This file loads only when working under `whatsapp/`.

Note: the `welcome` flow also spans `src/` Rust (`main.rs`, `gmail.rs`, `onedrive.rs`, `sync_contacts.rs`, `google_sheets.rs`) — documented here for reference. The safety rule "never commit real subscriber numbers" lives in the root `CLAUDE.md` so it is always loaded, including when editing those src/ files.

## WhatsApp Integration

- Located in `whatsapp/` directory — standalone Node.js scripts using Baileys (`@whiskeysockets/baileys` v7)
- **Requires Node.js ≥ 22** (Baileys v7 segfaults on Node 20.2; nvm path `/home/zeno/.nvm/versions/node/v22.22.2/bin/node`)
- `send.mjs` — send image to a WhatsApp group JID with optional caption; uses `process.exit(0)` after send to avoid close-handler hangs
- `send-doc.mjs` — send any file type (PDF, CSV, log, image, ...) to a JID *or* a plain phone number (`41787496544` is auto-suffixed to `@s.whatsapp.net`). Picks `image:` for png/jpg/jpeg, `document:` for everything else with a mime-type lookup table. Uses a 5-minute connection timeout (room for QR scan) and a 10-second post-send delay so async `saveCreds()` finishes writing `auth/creds.json` before node exits — without the delay, the next send needs a fresh QR.
- `list-groups.mjs` — list all groups with their JIDs
- `login.mjs` — dedicated login flow; auto-wipes stale sessions on 401 (loggedOut) and auto-reconnects on 515 (restartRequired, fires after first QR scan). Uses a `done` flag to prevent open/close race from reporting a spurious error when open fires moments before the socket closes.
- `login-qr.mjs` — same login flow but renders the QR additionally as a PNG (`/tmp/wa-login-qr.png`, via the `qrcode` package) and opens it in a window (`feh --auto-zoom`, fallback `xdg-open`). Use when the terminal ASCII QR is hard to scan. `--force` wipes the old session first. The send path (`check-and-send.mjs`) hangs silently waiting for a QR if `whatsapp/auth/creds.json` is missing — check that file exists before any send and re-login via this script if not. **Auto-reconnect loop**: WhatsApp only hands out ~6 QR refs per connection, then closes with `408` "QR refs attempts ended"; `main()` now loops (reconnect for a fresh QR batch, up to 10 min total; wipe+restart on 401/403) instead of dying — so a remote user relaying the ASCII QR always has a live QR. **⚠️ Do NOT abuse this into many scans:** too many device-link attempts trips a WhatsApp account block (phone popup "Verknüpfen neuer Geräte derzeit nicht möglich — Bitte versuche es später erneut"), which then fails BOTH QR and pairing until you wait hours. One clean scan; if it fails with that popup, stop and wait.
- `login-pair.mjs` — **experimental/unreliable** login via 8-char pairing code instead of QR (for remote/headless). Failed every time on 2026-07-10: 4× against Baileys `7.0.0-rc13` (phone "Gerät konnte nicht hinzugefügt werden"; socket stuck `registered:false`; close code 408 "attempts ended"), and retested on **stable Baileys 6.7.23 → same 408**, so it is NOT an RC-version bug — the pairing-code handshake is just broken for this account. **Prefer `login-qr.mjs`**; keep this only in case a future Baileys release fixes it.
- `leave-group.mjs` — supports comma-separated JIDs for bulk-leave
- `add-to-group.mjs` — add one or more numbers to a group (`groupParticipantsUpdate(..., "add")`); logs status 200 added / 403 privacy-blocked. Does *not* itself send an invite link.
- `send-group-mention.mjs` — post a **text message with @-mentions** to a group. Usage: `node send-group-mention.mjs <job.json>`, job = `{groupJid, text, mentions:[jid…]}`. The `text` must already contain the `@<number>` tokens (no `+`); `mentions` carries the JIDs Baileys writes into `contextInfo.mentionedJid`. Before sending it fetches `groupMetadata` and **warns for every mentioned JID that is not a group member** — for those WhatsApp renders the raw phone number to the whole group instead of a name. Driven by `welcome --announce` (below); 10s post-send delay for the `saveCreds()` flush, same as `send-doc.mjs`.
- `send-group-invite.mjs` — send a group **invite link** to one or more numbers. Fetches `sock.groupInviteCode(groupJid)` → `https://chat.whatsapp.com/<code>` and DMs it with a short note. Use when a direct add is blocked (403). Usage: `node send-group-invite.mjs <groupJid> <number> [<number>...]`.
- Session auth stored in `whatsapp/auth/` (excluded from git)
- First run requires QR code scan (WhatsApp → Linked Devices)
- Uses `fetchLatestBaileysVersion()` + `makeCacheableSignalKeyStore()` for stable connection
- Rust binary calls Node.js script as subprocess via `std::process::Command`; `find_node()` searches nvm, Homebrew, and system paths

## Pump Tsüri Welcome (`sync-contacts` / `welcome` alias)

End-to-end flow: Google Form (responses sheet) → SQLite → Baileys WhatsApp send, with a **Gmail-API e-mail fallback** for signups not reachable on WhatsApp (see `src/gmail.rs` below).

- **Auth**: service-account JSON at `whatsapp/google-sa.json` (gitignored). `src/google_sheets.rs` signs an RS256 JWT (`jsonwebtoken` crate), exchanges for an access token, then calls `spreadsheets.values.get`. No public sharing of the sheet — only the SA email needs Viewer access.
- **Sheet resolution**: input is a URL OR ID; `parse_sheet_id_and_gid()` extracts both. `resolve_sheet_title()` fetches metadata to map `gid` → sheet tab title (e.g. "Antwort", "Formularantworten 1"), then `fetch_values()` reads `<title>!A:Z`.
- **Presets**: `Commands::SyncContacts` takes an optional positional `variant`. `WelcomePreset` constants in `main.rs` bundle the per-variant defaults — sheet URL, DB filename, welcome text, email subject, default-image flag, column letters, group JID, `append_wa_invite`, and OneDrive docx fields. Each preset's defaults are applied via `unwrap_or_else` after clap parsing, so individual flags (`--sheet`, `--welcome`, `--mobile-col`, `--db`, …) still override on a per-field basis.
  - **Default sweep (no variant):** a bare `welcome` builds a **list of presets** and runs the greeting flow once per preset in a `for preset in presets` loop — currently `[pumper, schnupper]`, so **one command checks BOTH signup sheets** in a single run, each with its own DB + message. The loop only applies to the plain greet; the special sub-modes (`--invoice` / `--announce` / `--regen-docs` / `--mark-existing`, gathered into `is_special`) and every explicit variant force a **single** preset. The soft per-sheet early-exits (empty tab / nothing-new / `--dry-run` / PNG-fail / node-fail) are `continue`, not `return`, so one sheet never aborts the other.
  - `pumper` (default component) — Pump-Tsüri signup, `contacts.db`, columns C/J/D, image on, date col H, group *Pump Tiefenbrunnen*, `append_wa_invite: true`.
  - `schnupper` (default component) — Schnupperkurs/enquiry form (sheet `1d1CMpf…`, tab "Formularantworten 1"), `contacts_schnupper.db`, columns **D/B/C** (mobile/first/last) + email col H, **no date col** (col G "gewünschter Schulungstag" is free-text, not a date), image off, no group, **`append_wa_invite: false`** (the reply is just the booking-form link + signature, not a group invite). Welcome/email text points enquirers at the lesson-time Google **Form** (`forms/d/e/1FAIpQLScYsGWmMLLQvbUhC07f1vpuaEbMR6RtZsXKi4mwtIyFXK1ZOg/viewform`) so they pick their own slot. Backfilled once via `welcome schnupper --mark-existing` (28 historical rows) so only genuinely new enquiries get mailed.
  - `pp` (power pumper, one-minute achievement) — different sheet, `contacts_pp.db`, columns D/C/B, image off, Twint/cap message, **`append_wa_invite: false`** (since 20.08.2026): the group-invite link belongs to the *lessons* (pumper/schnupper), not the Power-Pumper flow, which is about the achieved minute + posting the cap. Still creates the OneDrive Mütze doc on both the e-mail and WhatsApp path (deduped per row_index).
  - `build` (build & pump event) — `contacts_build.db`, columns E/C/D (mobile/first/last), image off, English text-only welcome ("Welcome to the build and pump event {first}."). The signup sheet must be shared with the service-account email (`pegelstand@pegelstand.iam.gserviceaccount.com`) as Viewer or reads 403. To message only one new entry (e.g. just today's signup), `--mark-existing` to mark the whole pending set as greeted, `DELETE` that one row from `contacts`, then a normal run sends to it alone.
  - `hitachi` (Hitachi Pumpfoil event) — `contacts_hitachi.db`, columns E/C/D, image off, fixed event-confirmation text.
  - `in` / `indoor` (Indoor Pool-Pumpen, SSA Riedtli) — sheet `1yKwM8bV…` ("Indoor Pumpfoil, SSA Riedtli", tab "Formularantworten 1"), `contacts_indoor.db`, columns **E/C/D** (mobile/first/last) + email col B, **date col H** ("Datum der Teilnahme" → `{date}`), image off, group *Friday Pool Pump* (`120363406067038458@g.us`), `append_wa_invite: true`. Lessons are **every Friday 12.15–13.15** in the SSA Riedtli (Schulhaus Riedtli, Riedtlistrasse 41, 8006 Zürich; warm pool ~30 °C), **no sessions during school holidays** — season restarts after the Zürich Herbstferien (first lesson 23.10.2026). Welcome text carries a clean destination-only Maps link (no origin coords). Backfilled once via `welcome in --mark-existing` (32 historical contacts from 80 rows) so only genuinely new signups get contacted.
  - **`append_wa_invite`** (bool per preset): gates whether the gitignored `email-wa-invite.txt` group-invite link is appended to the mail body. `true` for pumper/build/hitachi/indoor, `false` for schnupper and (since 20.08.2026) **pp** — the group invite is a *lesson* thing, and the Power-Pumper mail (achieved minute → post the cap) has no lesson group to join.
- **Storage**: `whatsapp/contacts*.db` (SQLite via `rusqlite` with `bundled` feature — no system dep). `db_path(name)` and `open_db(name)` take the filename so multiple variants stay isolated. Two tables per DB:
  - `submissions` — full raw archive. PK = `row_index` (1-based, header is row 1). `data` column is a JSON object keyed by header name (source of truth for any schema evolution). Plus one TEXT column per sheet header, added on the fly via `ALTER TABLE` when a new header appears, and backfilled from JSON for existing rows so old data is immediately queryable without `json_extract`. Sanitization: lowercase, non-alnum → `_`, capped at 50 chars, deduped on collision.
  - `contacts` — registry of WhatsApp-confirmed recipients. PK = `jid`. FK `row_index` → `submissions(row_index)`. Inserted with `INSERT OR IGNORE` only **after** Baileys confirms the send.
- **Phone normalization** (`normalize_phone()` in `sync_contacts.rs`):
  1. Token-extraction: scans the cell for `+digits` or bare-digit runs (≥7 digits) bounded by separators (space/dash/parens/dot/comma/slash). Letters and multi-byte punctuation terminate a token. Multiple tokens per cell are kept as candidates.
  2. Multi-`+` rule: if multiple `+`-prefixed candidates and the lowercase string contains "whatsapp", pick the candidate nearest (byte distance) to the word. Handles `+41 77 902 18 93 (Whatsapp: +48696905840)` → `+48696905840`.
  3. CC normalization: strip `00` → `+`; leading `0` → `+<default_cc>`; bare 9-digit Swiss starting with `7` → `+41…` heuristic.
  4. Length sanity: 10–15 digits; `+41` numbers must be exactly 11 digits after `+`.
- **Node helper**: `whatsapp/check-and-send.mjs` — reads job JSON `{contacts, welcome, imagePath, groupJid}` from a temp file, connects via Baileys, calls `sock.onWhatsApp(jid)` per contact, sends image+caption (or text only if no `imagePath`), writes results JSON back. 1.5s pause between sends, 10s post-send delay for `creds.json` flush (same pattern as `send-doc.mjs`). If `groupJid` is set it also `groupParticipantsUpdate(..., "add")`s each recipient; on status **403** (recipient's privacy settings block a direct add) it automatically fetches the group invite code (`sock.groupInviteCode`, cached once per run) and DMs the person the invite link (`https://chat.whatsapp.com/<code>`), setting `invited: true` in the result. Log line: `→ privacy blocks add; invite link sent`.
  - **Delivery watching** (`WA_WATCH_DELIVERY=1`, set by pegelstand's `--watch-delivery`): the helper tracks each sent message's `key.id`, subscribes to `messages.update`, and records the highest ack seen (`SERVER_ACK=2` accepted-by-server / `DELIVERY_ACK=3` reached-device / `READ=4`). The post-send keepalive stretches from 10s to **50s** (unless `WA_KEEPALIVE_MS` is set explicitly) so the recipient's device has time to ack. At exit it re-writes `out.json` with `delivery` + `deliveryStatus` per result and prints a `Delivery summary:`. This is the built-in, **non-duplicating** way to confirm delivery — the same logic `diag-delivery.mjs` uses standalone, but folded into the normal welcome send (no second message). Rust reads it back via the optional `delivery`/`deliveryStatus` fields on `ResultEntry` and prints its own `Zustellung (Delivery-Quittungen):` summary.
- **PNG generation**: by re-invoking `std::env::current_exe()` with `svg --start … --end … --png` rather than duplicating chart code. Expected output path: `png/zurichsee_{start}_{end}.png`. Skipped if preset has `default_image: false` OR `--no-image` passed (effective = `no_image || !preset.default_image`).
- **CLI flags**: positional `variant`, then `--sheet`, `--mobile-col`, `--first-col`, `--last-col`, `--welcome`, `--db` (all `Option<String>` — preset supplies defaults); plus `--cc 41`, `--days 3`, `--no-image`, `--dry-run`, `--mark-existing`, `--regen-docs`, `--regen-rows "132,135"`, `--with-whatsapp`, `--watch-delivery` (`--force-email` still parses but is a no-op — e-mail is the default since 18.07.2026).
- **`--watch-delivery`**: after sending, keep the Baileys socket open ~50s and watch the delivery receipts so the real per-contact ack level is logged (`SERVER_ACK` vs `DELIVERY_ACK`) — confirms delivery **without** a duplicate send. Sets `WA_WATCH_DELIVERY=1` on the Node helper; the ack is read back from `out.json` and printed as `Zustellung (Delivery-Quittungen):`. Use it whenever you'd otherwise be tempted to re-send "just to check" (which duplicates). Related: [[feedback-whatsapp-send-no-kill]] and `whatsapp/diag-delivery.mjs` (the standalone one-number probe).
- **`--dry-run`** writes submissions (passive archive) but skips PNG generation, Node helper, and contacts insert.
- **`--mark-existing`** writes the current pending set straight into `contacts` without sending — one-shot backfill for an existing form population so the next run only messages genuine new submissions.
- **OneDrive-Doc-Erzeugung (pp):** the normal `welcome pp` run creates the personalised Mütze docx (`{{NAME}}/{{STRASSE}}/{{ORT}}` from the sheet, address col F) for **every freshly-greeted recipient — whether greeted by e-mail (the default) or WhatsApp**, deduped per `row_index`. (Historically it only fired for WhatsApp-`sent` recipients, so e-mail-first signups silently got no doc and needed a manual `--regen-docs`; fixed by collecting the mailed recipients into `mailed_recipients` and merging them into `sent_recipients` in `main.rs`.)
- **`--regen-docs`** (pp only) regenerates OneDrive Mütze documents for already-registered `contacts` **without** any WhatsApp send — recovery path when the OneDrive login failed on the original run, or to re-create docs (e.g. after fixing an address). Queries `contacts` (first_name/last_name/row_index), looks up the address from the live sheet row, parses + replaces placeholders, uploads. `--regen-rows "132,135"` restricts to specific 1-based row indices; empty = all registered contacts. Branch returns early before the send/PNG path.
- **⚠ WhatsApp verwirft Erstkontakte (confirmed 18.07.2026)**: a welcome DM to someone who has **never messaged Zeno first** is dropped server-side — silently. Group-adds fail loudly with `account_reachout_restricted`; the DM path gives **no ack at all** (not even `SERVER_ACK`), while `onWhatsApp()` still reports `exists: true`. Registration ≠ reachability. Proven both ways on one number the same day: before the recipient wrote, zero receipts and nothing arrived; minutes after she wrote, the identical send went `SERVER_ACK → DELIVERY_ACK → READ`. Baileys was current (`7.0.0-rc13` = npm `latest`), so this is WhatsApp policy, not a library bug. Diagnose with `--watch-delivery`: **no `SERVER_ACK` within ~50s = dropped**, never "recipient offline" (an offline phone still yields `SERVER_ACK`). A self-test to Zeno's own number always succeeds and therefore proves nothing about cold sends.
- **E-Mail ist der Standard-Erstkontakt (seit 18.07.2026)**: `welcome` / `welcome pp` mail **every** new signup that has an e-mail address, regardless of WhatsApp registration, and skip WhatsApp entirely unless `--with-whatsapp` is passed. Rationale above. Signups **without** an e-mail address are listed under `⚠ … ohne E-Mail-Adresse — bitte manuell kontaktieren` instead of being silently marked greeted. **Invalid/short phone number + valid e-mail (added 02.08.2026):** a signup whose mobile cell fails `normalize_phone` (one digit short, or a name typed into the number field) is no longer dropped as `ungültig` — if the row has a valid e-mail it routes to the e-mail fallback with an extra **PS asking for the correct WhatsApp number**, and is marked greeted via a **stable synthetic jid `email:<addr>`** so it is not re-mailed on later runs. The `Zeile N: ungültige Nummer … → E-Mail-Fallback` notice fires only *after* the known-jid dedup, so the number-check acts only on genuinely **new** sign-ups; the pre-existing invalid rows were backfilled as greeted. Invalid number **and** no e-mail is still surfaced as unreachable (`… (keine E-Mail — übersprungen)`, counted under `Ungültig (ohne E-Mail)`). E-mail-only rows are excluded from the WhatsApp job (their jid is synthetic, not a real device). Note the Google **Forms REST API cannot** set the form-side regex validation (`TextQuestion` exposes only `paragraph`) — that front-line check must be added via Apps Script (`requireTextMatchesPattern`), not `forms.batchUpdate`. The gitignored `whatsapp/email-wa-invite.txt` (same pattern as `email-signature.txt` → never commit) is appended to the mail body. **Since 18.07.2026** it holds a one-tap **group invite link** (`chat.whatsapp.com/<code>`, *Pump Tiefenbrunnen*) asking first-timers to join the group; before that it held a `wa.me/<nr>?text=<emoji>` link. **Joining the group lifts the DM block** — verified 18.07.2026: Matthieu joined and posted → `READ (4)`; **Filippo and Rossella joined and never posted → `DELIVERY_ACK (3)`**, which is the decisive pair, since it shows membership alone suffices and no inbound message is needed. - **E-Mail-Versand (`src/gmail.rs`)**: the welcome goes out by e-mail — same text, with the Zürichsee PNG attached. Sent from `zdavatz@gmail.com` via `gmail::Mailer::autodetect()`, which picks the transport (see **`whatsapp/EMAIL_SETUP.md`**): (1) **SMTP + Gmail App Password** (`SmtpSender`, `lettre` over `smtp.gmail.com`) if `~/.config/pegelstand/gmail-app-password.txt` (or `$PEGELSTAND_GMAIL_APP_PASSWORD`) exists — the recommended, no-expiry path (2FA required; note an app password also grants IMAP read, so `chmod 600`); else (2) the **Gmail API** (`users.messages.send`, `GmailSender`). Gmail-API auth (`GmailSender::from_credentials()`) prefers our **own** dedicated OAuth client via the token file `whatsapp/google-oauth-token.json` (gitignored, `authorized_user` shape: `client_id`/`client_secret`/`refresh_token`) minted by the one-time helper **`cargo run --release --bin gmail_auth`** (loopback OAuth against the Desktop client in `whatsapp/google-oauth-client.json`, scope `gmail.send`, `access_type=offline&prompt=consent`, port override via `$PEGELSTAND_GMAIL_OAUTH` for the token path). The e-mail column is auto-detected from the sheet header (any column whose name contains "mail"). The recipient's `Email` is added to `Pending`; after a successful send they are `insert_contact()`'d (marked greeted) exactly like a WhatsApp recipient, so they are never re-mailed. Per-preset `email_subject` (with `{first}` etc. placeholders) sets the subject line. **Auth gotcha (now automated by `gmail_auth`)**: the stock gcloud OAuth client (`764086051850-…`) is **not allowed to request `gmail.send`** — as of 2025/26 it errors with `cloud-platform scope is required` and Google shows **"Diese App ist blockiert"**, so `gcloud auth application-default login --scopes=…gmail.send` is a dead end. You must use the project's **own** Desktop OAuth client; `gmail_auth` runs that loopback (binds `127.0.0.1:0`, opens the consent URL, catches the redirect `?code=…`, exchanges it, writes the token file). Gmail API must be enabled on the quota project (`gcloud services enable gmail.googleapis.com --project pegelstand`). `gmail.send` is a **sensitive** (not restricted) scope → **no CASA security audit**. Publishing-status caveat that bit us: in **Testing** mode (with `zdavatz@gmail.com` as test user) it works without verification **but every refresh token expires after exactly 7 days** — that is what killed the June token (`invalid_grant: expired or revoked`). Files `whatsapp/google-oauth-client.json` (downloaded Desktop client) + `whatsapp/google-oauth-token.json` (minted, chmod 600) are both gitignored; nothing secret is committed.

Participant is matched by name in the sheet (exact match preferred, else unique substring). **Regulars sign up repeatedly, so a bare name usually hits several rows** — the error then lists each hit *with its lesson date*, and `--invoice-date <heute|morgen|übermorgen|25.07.2026|2026-07-25>` picks the lesson (parsed by the same `parse_announce_date`/`parse_sheet_date` helpers as `--announce`). **Datum = Lektionsdatum** (`date_col`, so pumper-only — a variant without a date column errors), Betrag default **CHF 65** (`--betrag N` to override), recipient = name + mobile. Keep any example numbers in source fictitious (`0XX XXX XX XX`) and don't use real participant names in help/error text.

Datumsformate im Sheet werden tolerant gelesen (`25.07.2026`, `25.7.2026`, ISO, mit Zusatz wie `25.07.2026 (Sa)`).
  - Rohtext enthält `@<Nummer>`; **WhatsApp rendert daraus den Anzeigenamen — aber nur, wenn die Person in der Gruppe ist.** Bei Nicht-Mitgliedern erscheint die **Telefonnummer** für alle sichtbar. `send-group-mention.mjs` prüft darum vorher die `groupMetadata` und **bricht ab (exit 2), ohne zu senden**, sobald ein Erwähnter kein Mitglied ist — die betroffenen Nummern werden aufgelistet. Bewusst trotzdem posten: `--announce-allow-nonmembers` (setzt `WA_ALLOW_NONMEMBER_MENTIONS=1`). Sauberer ist, die Leute vorher per `add-to-group.mjs` / `send-group-invite.mjs` in die Gruppe zu holen.
  - **Pro Nummer nur eine Erwähnung** — teilen sich zwei Personen eine Nummer (Paar-Anmeldung), kann WhatsApp sie nicht getrennt taggen; die zweite wird auf der Konsole als „teilt sich eine Nummer" ausgewiesen. Anmeldungen **ohne** gültige Nummer hängen als **Klartext-Name** an die Liste, statt zu fehlen.
  - **`--dry-run` zeigt Empfängerliste + Rohtext, ohne zu senden** — vor jedem echten Post sinnvoll, weil ein Gruppenpost nicht zurückholbar ist.
- **Tests**: `cargo test --release sync_contacts` — synthetic placeholder numbers (000-padded / US 555 fiction range) covering all parser branches. Never commit real subscriber numbers as test inputs.
